# Implicit state machines

An implicit state machine is a lifecycle the code enforces by convention instead of by structure: the states and legal transitions exist, but nobody wrote them down, so illegal states are reachable.

This skill runs in two phases. Phase 1 changes no code and always ends in a written report. Phase 2 converts one machine at a time.

A request to fix state bugs is still both phases, in order. The report comes first. Every conversion follows every Phase 2 step. Deadlines and "don't wait on me" change who answers the gate question below; they do not remove steps.

## Phase 1: Audit (read-only)

### What counts

Search for meaning, not just patterns. Look for:

- **Boolean clusters**: two or more flags on one entity or component that are not independent (`isLoading`, `isError`, `hasSubmitted`, `isOpen`).
- **Status fields with scattered writes**: a string or enum column or property assigned from several places with no single transition function.
- **Nullable-timestamp lifecycles**: combinations such as `published_at`, `archived_at`, `deleted_at`, `paid_at` that together encode a state.
- **Multi-step flows**: wizards, checkout, onboarding, auth, uploads, where step order lives in component state, URL params, or session.
- **Async and job lifecycles**: retries, queues, webhooks, sync, polling, connection handling, optimistic updates.
- **Agent and tool loops**: turn state, tool-call pending/resolved, approval gates, cancellation.
- **Implied state**: state derived from the presence or absence of related rows, files, or locks.

Ignore independent flags (a dark-mode toggle next to a loading flag is not a machine) and anything already modeled explicitly.

### What to record for each machine

- **Name and location**: the entity or flow, and the files that hold it.
- **States**: the real ones, named, including ones the code never names.
- **Transitions**: from, to, trigger, and every place in the code that performs the write.
- **Reachable impossible states**: specific combinations the code permits but should not (for example loading and error both true, or refunded and shipped). Cite the path that reaches each one. If none can be shown, say so.
- **Unhandled transitions**: events arriving in a state that has no handling for them (double submit, late webhook, cancel during retry).
- **Blast radius**: who is affected when it goes wrong (user-visible, data integrity, money, internal only).
- **Existing test coverage** of the lifecycle.

### Ranking

Rank by bug risk, highest first: reachable impossible states with data or money impact, then user-visible stuck or wrong states, then scattered writes with no demonstrated bug, then cosmetic.

### Report

Deliver the report as a ranked list, one section per machine, with a one-line recommendation each: convert, convert lightly, or leave alone (with the reason). Lead with a short summary table: machine, location, risk, recommendation.

### The gate

What happens after the report depends on what the request asked for.

| The request | After the report |
|---|---|
| Asks to find, audit, or list. It does not ask for fixes. | Stop and ask which machines to convert. If nobody is there to answer, write the report to `docs/state-machines.md` (or the repo's existing docs location) and end. |
| Names the machines to convert. | Convert those machines. |
| Asks for fixes, names no machine, and the user is there. | Stop and ask which machines to convert. |
| Asks for fixes, names no machine, and the user said not to wait. | Write the report to `docs/state-machines.md` and commit it alone. Then convert, in rank order, each machine whose entry shows a reachable impossible state with money, data, or user-visible impact. Leave the others in the report. |

A request that only asks for an audit never becomes Phase 2 on your own judgment.

## Phase 2: Convert (only the chosen machines, one at a time)

Finish every step for one machine before you open the next machine's files.

1. **Pin this machine's current behavior, and commit those pins alone.**
   - Write characterization tests for every transition in the machine's audit entry and for each reachable impossible state as it behaves today.
   - Run the full suite against the unchanged code and read the result. Commit only when it shows every test passing. A pin that fails is a wrong pin: fix the pin, not the code, and run again.
   - Make one pins commit per machine. It holds only that machine's pins, it passes on its own, and it lands before you edit any non-test file of this machine.
   - Pins are part of converting; they are not optional extra tests. Without them, nobody can tell what the conversion changed.
   - If the user says the existing tests already cover the machine, check that claim. List each transition and impossible state from the audit entry beside the existing test that exercises it. Write pins for the ones with no test, and report what you found.
2. **Pick the lightest explicit form that removes the impossible states**, in the stack's own idiom:
   - A discriminated union, sum type, or enum replacing a boolean cluster.
   - A single transition function or transition table that owns every write to the status.
   - A database check constraint or enum type where the state is persisted.
   - A state machine library only when the machine has hierarchy, parallel regions, or timers that justify it, or when the repo already uses one.
3. **Give every state its own stored value.** Do not store one state as a marker inside another, such as "cancelled" kept as `failed` plus a special error string. That builds a new implicit machine. If the storage cannot hold a state the machine needs, that is a stored-representation change: follow step 6.
4. **Route every write through the one transition point.** Illegal transitions fail loudly in development and are handled deliberately in production (reject, log, or no-op, chosen per case and stated).
   - For events that arrive from outside (webhooks, queues, retried requests), find out what the sender does on an error before you choose. An exception can make a provider retry forever.
   - If nobody is there to choose, reject the event, leave the stored state unchanged, and log it. Do not add compensating actions, such as refunds or notifications, that nobody asked for.
5. **Plan for rows already stored in an impossible state.** The old code could write them, so assume they exist. Give the query that finds them. Read paths must not start raising on them: map each combination to a named state, and say which. Repairing the rows is a data migration: follow step 6.
6. **Keep external contracts stable**: API shapes, database columns, event names, and persisted values do not change unless the user approved a migration.
   - Existing tests are contracts too. They must pass unmodified. If one would have to change, including to accept an added field, treat that as a contract change.
   - Where a stored representation must change, write the migration and the backfill, and say so before doing it.
   - If nobody is there to approve, do not make the change. Leave that behavior as pinned and list it under Open decisions.
7. **Update the pins deliberately.** The conversion should change only the pins for impossible states the audit listed. Edit those pins in place to assert the new behavior. Every other pin stays as written. If another pin fails, the conversion broke something: fix the code, not the pin. A bug that is not one of the audit's impossible states stays pinned; fixing it is a separate, named change.
8. **Run the full test suite** before each commit. Add tests for transitions that were previously unhandled.
9. **Commit the conversion for this machine alone**, after its pins commit, so each conversion can be reviewed and reverted on its own. Never put two machines in one commit.

## Final report for Phase 2

Give each converted machine these lines, in this order. Write "none" where a line is empty.

- **Pins**: how many, the command that ran them, the result against the unchanged code, and the pins commit.
- **Impossible states closed**: each one from the audit entry, whether it is now unrepresentable or rejected, and the test that proves it.
- **Behavior changes**: each pin you edited, as old behavior → new behavior.
- **Choices made without the user**: each event-handling choice from step 4.
- **Contracts**: unchanged, or what changed and who approved it.
- **Stored impossible rows**: the query that finds them and how reads treat them.
- **Open decisions**: everything left as pinned because it needs approval.
- **Not verified**: anything you could not check (no tests for an area, no way to run the app, no lint or type check). State it plainly instead of claiming nothing broke.

Before you report done, the pins passed before the change, the full suite passes after it, and lint and type checks pass where the repo has them.

## The three audiences

Every conversion should be checkable against all three:

- **Users (UX)**: each state has a deliberate presentation. No stuck spinners, no blank screens, no actions offered that the current state cannot accept.
- **Developers (DX)**: states and transitions are defined in one place, exhaustiveness is checked by the compiler or a test, and adding a state forces every consumer to handle it.
- **Agents (AX)**: the current state and the legal next transitions are readable without inferring them from several fields. Expose them where an agent would look: a typed `state` field in API responses, a `can`/`allowedTransitions` list, clear error messages naming the current state and why a transition was rejected, and a short entry in the repo docs listing each machine with its states and transitions. Step 6 still applies: add a field to an existing response only when no existing test or consumer pins its exact shape.

If a proposed change helps one audience at another's expense, say so in the report instead of proceeding.

## When not to formalize

- Two flags local to one small component with no demonstrated bad state.
- Code scheduled for deletion or rewrite.
- Machines where the conversion needs a risky data migration and the demonstrated risk is cosmetic.

Record these in the report as "leave alone" with the reason, so the next audit does not rediscover them.

## Shortcuts that look reasonable

| Thought | What to do |
|---|---|
| "They asked for fixes, so the report can wait." | Write the report first. It decides which machines get converted and what the pins must cover. |
| "They said the existing tests cover it." | Check the claim against the audit entry (step 1). Write the missing pins. |
| "There is no column for this state, so I'll store it as another state plus a note." | That is a new implicit machine (step 3). Leave the behavior pinned and list it under Open decisions. |
| "These three machines are small; one pass and one commit is faster." | One machine at a time: pins commit, then conversion commit. |
| "The new field is additive, so I can update the old test." | An existing test that must change is a contract change (step 6). |
