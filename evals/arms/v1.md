# Implicit state machines

An implicit state machine is a lifecycle the code enforces by convention instead of by structure: the states and legal transitions exist, but nobody wrote them down, so illegal states are reachable.

This skill runs in two phases with a hard stop between them. Phase 1 changes no code.

## Phase 1: Audit (read-only)

### What counts

Search for meaning, not just patterns. Look for:

- **Boolean clusters**: two or more flags on one entity or component that are not independent (`isLoading`, `isError`, `hasSubmitted`, `isOpen`).
- **Status fields with scattered writes**: a string or enum column or property assigned from several places with no single transition function.
- **Nullable-timestamp lifecycles**: combinations such as `published_at`, `archived_at`, `deleted_at`, `paid_at` that together encode a state.
- **Multi-step flows**: wizards, checkout, onboarding, auth, uploads, where step order lives in component state, URL params, or session.
- **Async and job lifecycles**: retries, queues, webhooks, sync, polling, connection handling, optimistic updates.
- **Agent and tool loops**: turn state, tool-call pending/resolved, approval gates, cancellation.
- **Implied state**: state derived from the presence or absence of related rows, files, or locks.

Ignore independent flags (a dark-mode toggle next to a loading flag is not a machine) and anything already modeled explicitly.

### What to record for each machine

- **Name and location**: the entity or flow, and the files that hold it.
- **States**: the real ones, named, including ones the code never names.
- **Transitions**: from, to, trigger, and every place in the code that performs the write.
- **Reachable impossible states**: specific combinations the code permits but should not (for example loading and error both true, or refunded and shipped). Cite the path that reaches each one. If none can be shown, say so.
- **Unhandled transitions**: events arriving in a state that has no handling for them (double submit, late webhook, cancel during retry).
- **Blast radius**: who is affected when it goes wrong (user-visible, data integrity, money, internal only).
- **Existing test coverage** of the lifecycle.

### Ranking

Rank by bug risk, highest first: reachable impossible states with data or money impact, then user-visible stuck or wrong states, then scattered writes with no demonstrated bug, then cosmetic.

### Report and stop

Deliver the report as a ranked list, one section per machine, with a one-line recommendation each: convert, convert lightly, or leave alone (with the reason). Lead with a short summary table: machine, location, risk, recommendation.

Then stop and ask which machines to convert. Do not start Phase 2 without an explicit choice. If running unattended, write the report to `docs/state-machines.md` (or the repo's existing docs location) and end there.

## Phase 2: Convert (only the chosen machines, one at a time)

For each machine, in this order:

1. **Pin current behavior.** Write characterization tests covering every existing transition and the externally visible behavior in each state. Run them and confirm they pass before changing anything. If a current behavior is a bug, pin it anyway and flag it; fixing it is a separate, named change.
2. **Pick the lightest explicit form that removes the impossible states**, in the stack's own idiom:
   - A discriminated union, sum type, or enum replacing a boolean cluster.
   - A single transition function or transition table that owns every write to the status.
   - A database check constraint or enum type where the state is persisted.
   - A state machine library only when the machine has hierarchy, parallel regions, or timers that justify it, or when the repo already uses one.
3. **Route every write through the one transition point.** Illegal transitions fail loudly in development and are handled deliberately in production (reject, log, or no-op, chosen per case and stated).
4. **Keep external contracts stable**: API shapes, database columns, event names, and persisted values do not change unless the user approved a migration. Where a stored representation must change, write the migration and the backfill, and say so before doing it.
5. **Run the full test suite**, plus the new characterization tests. Add tests for transitions that were previously unhandled.
6. **Commit per machine** so each conversion can be reviewed and reverted on its own.

## The three audiences

Every conversion should be checkable against all three:

- **Users (UX)**: each state has a deliberate presentation. No stuck spinners, no blank screens, no actions offered that the current state cannot accept.
- **Developers (DX)**: states and transitions are defined in one place, exhaustiveness is checked by the compiler or a test, and adding a state forces every consumer to handle it.
- **Agents (AX)**: the current state and the legal next transitions are readable without inferring them from several fields. Expose them where an agent would look: a typed `state` field in API responses, a `can`/`allowedTransitions` list, clear error messages naming the current state and why a transition was rejected, and a short entry in the repo docs listing each machine with its states and transitions.

If a proposed change helps one audience at another's expense, say so in the report instead of proceeding.

## When not to formalize

- Two flags local to one small component with no demonstrated bad state.
- Code scheduled for deletion or rewrite.
- Machines where the conversion needs a risky data migration and the demonstrated risk is cosmetic.

Record these in the report as "leave alone" with the reason, so the next audit does not rediscover them.

## Verification before reporting done

- Characterization tests passed before and after the change.
- Full suite passes; lint and type checks pass.
- Each impossible state listed in the audit is now unrepresentable or rejected, with a test proving it.
- State anything that could not be verified (no tests for an area, no way to run the app) plainly, instead of claiming nothing broke.
